# 개발 직무 맛보기 실험실 PRD v0.2

2026-11-22

## 개요

개발 직무 맛보기 실험실은 컴퓨터학부 학생이 프론트엔드(JavaScript), 백엔드(Python), 데이터 분석(Python)의 작은 작업을 세 가지 방식으로 직접 해보는 진로 탐색 서비스다. 세 방식은 직접 고치기, AI가 쓴 코드 검수하기, AI에게 지시하기다. 학생은 어떤 분야와 어떤 작업 방식에 흥미를 느꼈는지 비교하고 다음 학습이나 프로젝트를 고른다.

이 서비스의 핵심 메시지는 다음과 같다. **AI가 코드를 써줘도, 그 코드가 맞는지 판단하려면 결국 언어와 분야를 알아야 한다.** 그래서 언어 체험은 유지하고, AI와 함께 일하는 방식을 두 번째 축으로 더한다.

이 문서는 구현을 위한 초안 v0.2다. 문제의 빈도와 사용자 반응은 검증할 가설로 두고, 첫 출시 범위와 수용 기준을 제안한다.

v0.1 대비 주요 변경:

- 체험 구조를 '분야 3개'에서 '분야 3개 × 작업 방식 3개'로 확장했다.
- 결과와 추천을 분야 축과 방식 축 두 갈래로 나눴다.
- v0.1 검토에서 나온 불일치를 수정했다. 사전 명확성 문항 누락, 7일 후 확인 대상, 파일럿 소요 시간, 추천 규칙의 중복과 누락, 비교 요약 횟수가 해당한다.

세부 변경 내역은 부록에 정리했다.

## 01 문제 상황 인식

컴퓨터학부 학생이 개발 직무를 고를 때 간격이 두 가지 생길 수 있다. 하나는 직무 이름과 실제 작업 사이의 간격이고, 다른 하나는 AI 코딩 도구가 퍼지면서 생긴 간격이다. 학생은 코드를 직접 쓰는 비중이 줄어든 환경에서 자신이 어떤 일을 맡게 될지, 그 일을 좋아할지 판단하기 어렵다.

프론트엔드와 백엔드라는 직무는 여전히 있다. 다만 그 안에서 사람이 하는 일은 바뀌고 있다. 무엇을 만들지 정하고, AI 결과를 검증하고, 문제를 추적하는 일의 비중이 커진다. 전공 수업은 주로 직접 작성을 다루므로, AI와 함께 일하는 경험은 수업 밖에 머물러 있다.

다음은 검증할 대표 상황이다.

- 수업과 팀 프로젝트에서 맡아본 역할이 제한돼 다른 분야를 선택할 근거가 부족하다.
- 분야를 알아보려고 강의를 시작했지만 설치와 문법 학습에서 멈춘다.
- 처음 접한 언어나 도구가 어려웠던 경험을 그 분야 자체에 대한 흥미 부족으로 받아들인다.
- AI 코딩 도구로 과제를 끝내봤지만, 결과가 맞는지 스스로 판단해본 경험은 적다.
- AI가 코드를 쓴다면 특정 언어나 분야를 깊게 배울 필요가 있는지 확신하지 못한다.
- 콘텐츠를 본 뒤에도 다음 학기 과목과 해볼 프로젝트를 결정하지 못한다.

예상 사용자 발화는 "AI가 코드를 짜주는데, 내가 백엔드를 제대로 배워야 하는지, 내가 그 일을 좋아할지 모르겠다"이다. 실제 인터뷰에서는 이 문장을 유도하지 않고 최근 직무 탐색과 AI 도구 사용 경험을 확인한다.

## 02 대상 사용자와 사용 시점

첫 대상은 변수, 조건문, 반복문, 함수의 기초를 배운 컴퓨터학부 1~3학년이다. 한 분야의 실무 능력을 평가받으려는 사람보다, 서로 다른 작업을 해보고 다음 학습 방향을 고르려는 사람에게 집중한다.

| 사용자 | 현재 상황 | 원하는 변화 |
| --- | --- | --- |
| 전공 입문 학생 | 분야 이름은 알지만 직접 해본 일이 적다 | 흥미가 생기는 작업을 발견한다 |
| 첫 팀 프로젝트 준비 학생 | 프론트와 백엔드 중 역할을 정해야 한다 | 작은 경험을 바탕으로 역할을 선택한다 |
| 관심 분야를 바꾸려는 학생 | 한 분야만 경험해 다른 분야를 판단하기 어렵다 | 기존 경험과 새 작업을 비교한다 |
| AI 도구를 쓰지만 진로와 연결하지 못한 학생 | AI로 과제는 하지만 자신이 잘하는 부분을 모른다 | AI와 일할 때 자신이 맡고 싶은 역할을 찾는다 |

사용 시점은 수강 신청 전, 동아리나 팀 프로젝트의 역할 배정 전, 방학 학습 계획을 세울 때다. 완전한 프로그래밍 입문 교육, 취업 역량 인증, AI 도구 사용법 강의는 첫 버전에서 제외한다.

## 03 목표와 핵심 가치

목표는 사용자가 두 트랙 이상을 체험한 뒤 세 가지를 자신의 말로 설명하게 만드는 것이다. 어떤 분야와 어떤 작업 방식이 흥미로웠는지, 무엇 때문에 어려웠는지, 다음에 무엇을 해볼지다.

핵심 가치는 네 가지다.

1. 별도의 개발환경 설치 없이 실제 JavaScript와 Python 코드로 시작한다.
2. 같은 서비스의 서로 다른 문제를 풀며 분야의 차이를 경험한다.
3. 같은 분야 안에서 직접 고치기, AI 코드 검수하기, AI에게 지시하기를 모두 해보며 AI와 함께 일하는 방식의 차이를 경험한다.
4. 실행 결과, 선택 이유, 자기 회고를 함께 보고 다음 행동을 정한다.

출시 버전에서는 프론트엔드, 백엔드, 데이터 분석 세 분야를 제공한다. 세 분야가 모든 개발 직무를 포괄한다고 표현하지 않는다. 또한 AI가 특정 직무를 대체한다거나 어떤 방식이 더 유망하다고 단정하지 않는다. 서비스는 선택에 필요한 경험을 제공할 뿐이다.

## 04 문제 가설과 사전 검증

개발 착수 전(0주차)에 컴퓨터학부 학생 8명 내외를 인터뷰한다. 미션 설계와 동시에 진행하면 결과를 반영할 시간이 없으므로 앞으로 당겼다. 학년, 기존 경험, AI 도구 사용 정도가 다른 학생을 포함하고 가설과 반대되는 사례도 기록한다.

| 가설 | 확인할 질문과 행동 | 초기 판단 기준 |
| --- | --- | --- |
| H1. 직접 해본 작업이 부족해 분야 선택이 어렵다 | 최근 분야를 선택하거나 포기한 과정과 참고한 근거를 묻는다 | 8명 중 5명 이상에게 구체적인 경험 부족 사례가 있으면 우선 해결한다 |
| H2. 설치와 선행 학습이 체험을 지연한다 | 시작 후 실제로 무언가를 수정하기까지의 과정과 포기 지점을 확인한다 | 반복되는 장애를 체험의 시작 흐름에서 제거한다 |
| H3. AI 도구가 퍼지면서 분야와 언어 학습에 대한 판단이 더 어려워졌다 | AI 도구를 쓴 최근 과제와, 그 경험이 학습·진로 계획에 준 영향을 묻는다 | 8명 중 4명 이상이 구체적인 혼란 사례를 말하면 방식 축을 유지한다 |
| H4. AI 결과를 검증해본 경험이 적다 | AI가 만든 코드가 틀렸던 경험과 그때 어떻게 알아차렸는지 묻는다 | 대부분이 검증 절차 없이 사용했다면 검수 미션을 우선한다 |
| H5. 작은 작업도 다음 선택에 도움이 된다 | 첫 미션 시제품을 사용한 뒤 다음에 해보고 싶은 일을 설명하게 한다 | 막연한 직무 이름보다 구체적인 다음 행동이 나오는지 확인한다 |

이 기준은 프로젝트 진행을 위한 임시 기준이며 현재 조사 결과가 아니다. H3이 기각되면 방식 축을 줄이고 v0.1의 분야 중심 구조로 돌아간다. 경험 부족보다 채용 정보나 학습 비용이 더 큰 문제로 확인되면 대상 사용자와 제공 가치를 다시 좁힌다.

## 05 체험 콘텐츠 설계

체험은 분야 3개와 작업 방식 3개를 교차한 **9개 미션**으로 구성한다. 한 트랙(분야)에 들어가면 세 방식의 미션을 차례로 수행한다.

### 공통 사례

공통 사례는 "교내 행사 신청 서비스 개선"이다. 학생은 트랙마다 다른 역할을 맡되 서비스의 배경과 용어를 다시 익히지 않는다. 실제 학생 개인정보 대신 제작한 예시 데이터만 사용한다.

### 두 축

| 분야 | 언어 | 요청받은 일 | 확인할 작업 성격 |
| --- | --- | --- | --- |
| 프론트엔드 | HTML, JavaScript | 신청 가능한 행사를 쉽게 찾게 해주세요 | 화면 반응, 사용자 관점의 개선 |
| 백엔드 | Python | 중복 신청과 정원 초과를 막아주세요 | 규칙 해석, 예외 조건, 데이터 일관성 |
| 데이터 분석 | Python(표준 라이브러리) | 다음 행사 운영에서 무엇을 개선할지 알려주세요 | 데이터 정리, 비교 기준, 수치 해석 |

| 작업 방식 | 사용자가 하는 일 | 확인할 작업 성격 |
| --- | --- | --- |
| 직접 고치기 | 제공된 코드를 직접 수정하고 실행한다 | 문법과 로직을 손으로 다루는 일 |
| AI 코드 검수하기 | AI가 쓴 코드를 읽고 숨은 버그를 찾아 고친다 | 코드 읽기, 경계 조건 찾기, 검증 |
| AI에게 지시하기 | 요구사항을 글로 쓰고, AI가 만든 코드를 테스트로 확인해 채택한다 | 요구사항 정의, 빠진 조건 찾기, 채택 판단 |

### 미션 9개

| 분야 | 직접 고치기 | AI 코드 검수하기 | AI에게 지시하기 |
| --- | --- | --- | --- |
| 프론트엔드 | 마감된 행사를 목록에서 숨기도록 필터 조건을 고친다 | '신청 가능' 표시 코드의 날짜 비교 버그를 찾는다 | 학과별 필터를 추가하도록 지시하고 화면 테스트로 확인한다 |
| 백엔드 | 중복 신청 검사 조건을 고친다 | 정원 초과 처리 코드의 경계값 버그를 찾는다 | 대기자 등록 기능을 지시하고 함수 테스트로 확인한다 |
| 데이터 분석 | 중복 신청 행을 제거하는 코드를 고친다 | 참여율 집계의 분모 오류를 찾는다 | 학년별 참여율 표를 지시하고 결과를 해석해 개선안을 쓴다 |

검수 미션의 코드는 실제 AI가 생성한 코드를 운영자가 검토하고, 학습 목적의 버그를 확인·배치한 고정 코드다. 사용자에게도 이 사실을 안내한다. 누가 풀든 같은 코드를 보므로 결과가 달라지지 않는다.

지시 미션은 모델이 아무 요구사항에나 맞는 코드를 내면 의미가 없다. 그래서 요청문에는 드러나지 않는 핵심 조건을 **숨은 테스트**로 둔다. 백엔드 예시는 "취소가 생기면 대기 1번이 승격된다"와 "대기자도 중복 등록을 막는다"다. 사용자가 이 조건을 요구사항에 적어야 테스트를 통과한다. 실패하면 요구사항을 고쳐 최대 3번까지 다시 지시할 수 있다. 생성된 코드를 직접 고쳐 채택해도 된다.

백엔드 체험은 요청과 응답을 흉내 낸 입력으로 업무 규칙을 다루며, 실제 서버 배포와 동시 접속 처리는 포함하지 않는다. 데이터 분석은 모델 학습이 아닌 기초 집계와 해석을 다루고, pandas 대신 `csv`, `collections` 등 표준 라이브러리만 쓴다. 실행기 최초 로딩을 줄이기 위해서다.

이 활동 구분은 웹 개발과 데이터 분야의 업무를 참고한 교육용 축약이다. 세부 직무와 실제 업무는 조직에 따라 달라질 수 있다. 참고: O\*NET Web Developers, O\*NET Data Scientists.

### 트랙 구성과 난이도

각 트랙은 약 30~40분을 목표로 설계한다. 이 시간은 사용성 테스트에서 조정하며 시간 제한이나 평가 점수로 쓰지 않는다.

1. 배경과 요청을 읽는다.
2. 필요한 문법을 3분 내외의 준비 예제로 확인한다.
3. 기존 코드를 실행하고 정상 상태를 확인한다.
4. 직접 고치기 미션을 해결한다.
5. AI 코드 검수하기 미션을 해결한다.
6. AI에게 지시하기 미션을 해결한다.
7. 수정·채택 이유를 짧게 설명한다.
8. 트랙 전체와 방식별로 흥미와 난이도를 회고한다.

방식 순서는 **직접 고치기 → 검수 → 지시**로 고정한다. 코드를 직접 만져봐야 AI 결과를 판단할 맥락이 생기기 때문이다. 순서가 방식별 흥미에 주는 영향은 파일럿에서 관찰한다.

온보딩에서 언어별 경험과 AI 도구 사용 경험을 따로 기록한다. 처음 접하는 언어에는 고정된 문법 안내를 제공한다. 트랙별 시간과 테스트 통과율은 언어 능력의 순위로 합산하지 않는다.

모든 미션은 운영자가 사전 작성하고 검수한다. AI가 사용자마다 새 문제나 정답 기준을 만드는 방식은 초기 범위에서 제외한다. 지시 미션에서 AI가 만드는 것은 코드뿐이고, 채점 기준은 고정 테스트다.

## 06 사용자 흐름과 화면

사용자는 다음 순서로 진행한다.

1. 비회원으로 시작한다.
2. 사전 질문에 답한다. 언어 경험, AI 도구 사용 경험, 탐색 목적, 탐색 명확성 5점 문항이다.
3. 외부 AI 전송 안내를 보고 동의 여부를 고른다.
4. 트랙을 고른다.
5. 준비 예제를 확인한다.
6. 직접 고치기, 검수하기, 지시하기 미션을 수행한다.
7. 트랙 회고를 제출하고 개별 결과를 본다.
8. 원하면 다른 트랙을 체험한다.
9. 두 트랙 이상이면 비교 결과를 보고 다음 활동을 고른다.
10. 마지막으로 같은 탐색 명확성 문항에 다시 답한다.

AI 전송에 동의하지 않으면 AI 힌트·회고 요약 대신 고정 힌트와 정형 결과를 제공한다. 지시 미션은 **'요구사항 고르기' 대체 미션**으로 바꾼다. 미리 작성한 요구사항 2개와 그에 대한 미리 생성한 코드를 보고, 어느 쪽이 테스트를 통과할지 예상한 뒤 확인하는 방식이다. 같은 대체 미션을 AI 장애 때도 쓴다.

| 화면 | 필요한 정보와 행동 |
| --- | --- |
| 시작 화면 | 무엇을 체험하는지, 트랙당 예상 시간, 필요한 기초 지식, 설치 없이 시작하기 |
| 사전 질문 | Python·JavaScript 경험, AI 코딩 도구 사용 빈도, 기존 프로젝트 역할, 비교해보고 싶은 분야, 탐색 명확성("다음에 무엇을 배울지 얼마나 분명한가", 1~5점) |
| AI 사용 안내 | 어떤 내용이 외부 AI로 전송되는지, 동의하지 않아도 체험할 수 있다는 안내, 동의 선택 |
| 트랙 목록 | 각 트랙에서 실제로 할 작업 3가지, 준비 지식, 예시 결과물 |
| 작업 화면(직접·검수) | 요청사항, 코드 편집, 실행 결과, 테스트 결과, 힌트, 저장 상태. 검수는 'AI가 쓴 코드' 표시와 버그 위치 기록란 추가 |
| 작업 화면(지시) | 요구사항 입력란, 생성된 코드, 테스트 결과, 남은 지시 횟수, 채택·직접 수정 버튼 |
| 회고 화면 | 트랙 전체의 흥미·체감 난이도·재도전 의향(각 1~5점), 방식별 흥미 3문항(1~5점), 이유 서술 |
| 개별 결과 | 수행한 작업, 테스트 결과, 사용한 도움, 방식별 회고, 다음 작은 과제 |
| 비교 화면 | 두 트랙 이상의 분야별·방식별 회고를 나란히 확인하고 다음 활동 선택 |

트랙 순서는 사용자가 고른다. 첫 선택에 설명이 필요하면 직무 이름과 함께 "화면 반응 만들기", "신청 규칙 만들기", "숫자에서 개선점 찾기"를 보여준다. 한 트랙을 마쳐도 다른 트랙을 강제로 시작시키지 않는다.

## 08 AI API 활용 요구사항

AI는 두 가지 일을 맡는다. 하나는 사용자가 작업을 이해하고 경험을 되짚도록 돕는 일이고, 다른 하나는 지시 미션에서 코드를 생성하는 일이다. 코드의 실행 결과와 테스트 통과 여부는 정해진 실행기와 검증 코드가 판단한다.

### 기능별 역할

| 기능 | 입력 | 출력 | 제한 |
| --- | --- | --- | --- |
| 코드 생성(지시 미션) | 사용자 요구사항, 미션의 기존 코드와 함수 시그니처 | 지정된 함수·영역의 코드만 | 테스트와 숨은 조건은 입력에 넣지 않는다. 요구사항에 없는 기능을 스스로 추가하지 않도록 지시한다 |
| 단계별 힌트 | 미션 단계, 현재 수정 내용, 실패 사례, 이전 힌트 | 개념 설명, 확인할 위치, 작은 예시 순서의 도움 | 첫 응답부터 전체 정답을 주지 않는다. 검수 미션에서는 버그 위치를 바로 알려주지 않는다 |
| 오류 설명 | 실제 실행 오류와 검증 결과 | 쉬운 원인 설명과 다음 확인 항목 | 기록에 없는 오류나 실행 결과를 만들지 않는다 |
| 선택 이유 질문 | 사용자의 수정·채택 결과와 설명 | "이 경우에는 어떻게 될까요" 같은 후속 질문 | 직무 적합성이나 성격을 판정하지 않는다 |
| 회고 요약 | 수행 기록, 자기 평가, 사용자가 적은 이유 | 분야별·방식별 흥미와 어려움, 다음 활동 후보 설명 | 관찰 사실과 사용자 응답을 구분한다. 후보 자체는 09장 규칙이 정한다 |

예시 응답은 "중복 신청 처리는 통과했고 대기자 승격 사례는 아직 남아 있어요. 취소가 생겼을 때 어떻게 되어야 하는지 요구사항에 적었나요?"처럼 실제 테스트 기록을 근거로 한다.

### 코드 생성의 일관성

같은 요구사항이라도 생성 결과는 달라질 수 있다. 이를 다음과 같이 다룬다.

- 채점은 항상 생성된 코드를 고정 테스트로 한다. 같은 코드면 같은 결과다(F04).
- 생성 설정은 낮은 무작위성으로 고정하고, 같은 미션 버전에서 같은 요구사항 문장은 저장된 결과를 재사용한다.
- 요구사항, 생성 코드, 테스트 결과, 시도 번호를 함께 기록해 결과 리포트의 근거로 쓴다.
- 생성 코드는 사용자에게 먼저 보여주고 격리된 실행 영역에서만 실행한다. 서비스 서버에서 실행하지 않는다.

### 호출과 품질 관리

AI API는 서비스 서버를 통해 호출하고 브라우저에 API 키를 전달하지 않는다. 초깃값 한도는 다음과 같다.

| 항목 | 한도 |
| --- | --- |
| 힌트·질문 | 트랙당 4회 |
| 코드 생성 | 트랙당 3회(재지시 포함) |
| 회고 요약 | 트랙당 1회 |
| 비교 요약 | 두 번째 트랙 종료 시 1회, 세 번째 트랙 종료 시 1회 |
| 사용자당 최대 | 세 트랙 기준 (4+3+1)×3 + 2 = 26회 |

익명 식별자는 쿠키를 지우면 초기화되므로, 식별자 한도와 함께 IP 단위 호출 속도 제한을 둔다. 운영자는 전체 일일 비용 한도를 설정하고, 한도에 다다르면 고정 힌트와 대체 미션으로 전환한다. 같은 실패 상황의 고정 설명은 재사용한다.

힌트 응답은 짧은 설명, 다음 행동, 참조한 단계 ID를 포함한 구조로 받는다. 서버는 형식과 참조 ID를 검사하고 출력 길이를 제한한다. 사용자 코드와 문장은 분석할 자료로 전달하고 시스템 지시와 분리한다. 응답의 지시를 실행하거나 코드에 자동 적용하지 않는다.

입력은 현재 단계의 코드와 필요한 실행 기록으로 한정한다. 한 요청의 코드·자유 입력 합계는 2만 자 이내, 요구사항은 1,000자 이내로 제한하고 긴 로그는 오류 주변만 전달한다. 모델과 제공사는 한국어 설명 품질, 코드 생성 정확도, 제한된 입력에서의 일관성, 지연, 실제 비용을 평가한 뒤 선정한다.

### 출시 전 평가

- **힌트·요약:** 최소 30개 사례. 정상 풀이, 미완료, 문법 오류, 과도한 정답 요구, 지시 우회 문구, 빈 회고를 포함한다.
- **코드 생성:** 지시 미션마다 요구사항 사례 10개. 조건을 다 적은 것, 숨은 조건을 빠뜨린 것, 모호한 것, 정답 코드를 통째로 붙여넣은 것을 포함한다. 요구사항의 완성도와 테스트 통과 여부가 일치해야 한다.
- 기록과 다른 성공 주장, 적성 단정, 조건을 빠뜨렸는데 통과하는 생성이 나온 사례는 출시 전 수정하고 재검증한다.

## 09 결과 리포트와 추천 기준

결과는 작업 기록과 자기 회고를 분야 축과 방식 축으로 나눠 보여준다. "백엔드 적합도 92점"이나 "AI 활용 능력 상위 10%" 같은 종합 점수나 순위는 만들지 않는다.

| 구분 | 표시할 내용 | 해석 원칙 |
| --- | --- | --- |
| 수행 기록 | 미션별 시도 단계, 검증 사례별 통과 여부, 찾은 버그 수, 지시 횟수, 완료·미완료 | 해당 미션의 결과로 한정한다 |
| 도움 기록 | 사용한 힌트 단계, 정답 예시 열람 여부 | 실력 감점으로 쓰지 않는다 |
| 분야 회고 | 트랙별 흥미, 체감 난이도, 재도전 의향, 자유 서술 | 사용자의 응답임을 표시한다 |
| 방식 회고 | 직접·검수·지시 방식별 흥미 | 사용자의 응답임을 표시한다 |
| 비교 맥락 | 언어 경험, AI 도구 경험, 준비 예제 수행, 미션 버전, 대체 미션 여부 | 다른 트랙의 수치와 단순 우열 비교를 피한다 |
| 다음 행동 | 분야 축 후보 1개, 방식 축 후보 1개 | 사전 검수한 활동 목록에서만 제안한다 |

### 분야 축 결정표

트랙마다 위에서부터 차례로 확인해 처음 맞는 규칙 하나만 적용한다. 흥미는 I, 체감 난이도는 D, 재도전 의향은 R이고 모두 1~5점이다.

| 순서 | 조건 | 제안 |
| --- | --- | --- |
| 1 | 회고가 비어 있음 | 추천 보류. 회고 작성을 안내한다 |
| 2 | I ≥ 4, D ≥ 4 | 짧은 기초 보충 후 같은 트랙 재체험 |
| 3 | I ≥ 4, R ≥ 4 | 같은 분야의 확장 미션 |
| 4 | I ≥ 4 | 같은 분야의 관련 학습 주제(과목·자료) |
| 5 | I ≤ 3, 아직 하지 않은 트랙이 있음 | 다른 트랙 체험 |
| 6 | I ≤ 3, 세 트랙을 모두 함 | I가 가장 높은 트랙의 확장 미션. 모두 2점 이하이면 개발 외 진로 탐색 자료 |

순서를 두었으므로 두 규칙이 동시에 적용되지 않는다. 흥미와 난이도가 모두 높으면 재도전 의향과 관계없이 기초 보충이 먼저다. 두 트랙 이상이면 각 트랙의 결과를 나란히 보여주고, I가 가장 높은 트랙의 제안을 대표로 놓는다. 동점이면 사용자가 고른다.

### 방식 축 결정표

방식별 흥미는 수행한 모든 트랙의 같은 방식 점수 평균으로 계산한다.

| 조건 | 제안 |
| --- | --- |
| 직접 고치기가 가장 높고 4점 이상 | 해당 언어로 끝까지 직접 만드는 미니 프로젝트 |
| 검수하기가 가장 높고 4점 이상 | 코드 리뷰·테스트 작성 연습 미션 |
| 지시하기가 가장 높고 4점 이상 | 요구사항·명세 작성 연습 미션 |
| 최고점이 두 방식 이상에서 같음 | 후보를 모두 보여주고 사용자가 고른다 |
| 모든 방식이 3점 이하 | 방식 추천 보류. 방식별 차이만 보여준다 |

다음 행동 후보는 이 고정 규칙이 정하고, AI는 설명만 돕는다. 각 결과에는 수정한 작업과 회고를 다시 열 수 있는 근거를 연결한다. AI가 기록과 맞지 않게 요약하면 사용자가 수정하거나 신고할 수 있고, 원래 기록은 유지한다.

## 10 구현 방향과 데이터

### 권장 구성

브라우저 기반 웹 서비스로 구현한다. 화면과 코드 편집기는 React와 TypeScript를 후보로 둔다. 서버는 팀이 익숙한 프레임워크 하나를 골라 세션, 콘텐츠, AI 호출, 비용 기록을 맡긴다. AI를 위한 별도 서비스는 초기 필수 조건이 아니다.

방식별 구현 부담은 다르다.

- **직접 고치기:** 코드 편집, 격리 실행, 검증이 필요하다.
- **검수하기:** 직접 고치기와 같은 실행기를 쓰고, 추가로 버그 위치 기록란만 필요하다.
- **지시하기:** 서버의 코드 생성 호출, 생성 결과 캐시, 숨은 테스트가 추가로 필요하다. 가장 무겁다.

### 실행 영역과 격리

사용자 코드와 AI 생성 코드는 서비스 서버 프로세스에서 실행하지 않는다.

- 프론트엔드 코드는 서비스 화면과 분리된 별도 출처의 iframe에서 실행한다. 검증 스크립트는 같은 iframe 안에서 DOM 상태를 검사하고, 허용한 형식의 메시지로만 결과를 보낸다.
- 백엔드·데이터 체험의 Python은 Pyodide를 Web Worker에서 실행하는 방식을 검증한다. 실제 패키지 크기, 최초 로딩, 브라우저 호환성은 1주차에 측정한다. 참고: Pyodide Web Worker 공식 문서.
- Worker만으로 보안 격리가 완성된다고 가정하지 않는다. 실행 영역은 별도 출처로 분리하고 인증 정보와 저장소 접근을 차단한다.
- 외부 통신은 Pyodide 자원을 실행 영역 출처에 직접 올리고, CSP를 `connect-src 'self'`로 고정해 막는다. CSP는 실행 도중에 바꿀 수 없으므로 "초기화 후 차단" 방식은 쓰지 않는다.
- 실행 제한의 초기 기준은 1회 5초다. 초과하면 Worker를 종료한다. Pyodide 재로딩 대기를 줄이려고 예비 Worker 하나를 미리 띄워 두고 교체한다.
- 대용량 데이터와 임의 패키지 설치는 지원하지 않는다. 브라우저 자원 소모와 격리를 검증하지 못하면 임의 코드 체험을 공개하지 않고 비공개 기술 시제품에서 먼저 해결한다.

테스트는 브라우저에서 실행되므로 서버가 받는 통과 여부는 클라이언트가 보고한 값이다. 점수나 순위가 걸리지 않는 서비스이므로 조작 가능성은 허용한다.

## 11 예외 처리와 사용성 기준

어떤 장애가 생겨도 사용자의 작업을 보존하고 체험을 이어갈 수 있게 한다.

| 상황 | 제품 동작 |

| Python 실행기 최초 로딩 지연 | 다운로드 상태와 재시도를 제공한다. 준비되지 않은 상태에서 실행 버튼을 활성화하지 않는다 |
| 무한 반복 또는 실행 제한 초과 | 코드 초안을 보존하고 예비 Worker로 교체한다. AI 생성 코드도 같은 방식으로 처리한다 |

| 서버 저장 실패 | 마지막 서버 저장 시각과 미저장 상태를 표시하고 코드를 복사·다운로드할 수 있게 한다 |
| 트랙 중도 종료 | 시도 기록을 저장하고 회고 또는 이어하기를 선택하게 한다 |
| 지원하지 않는 기기 | 시작 전에 제한을 알리고 기존 작업을 보존한다 |

주 사용 환경은 데스크톱 최신 Chrome과 Edge로 잡고 출시 시 지원 버전을 명시한다. 모바일에서는 소개와 결과 조회만 지원하고 코드 편집은 첫 버전에서 제외한다. 주요 흐름은 키보드로 조작할 수 있어야 하고, 성공·실패를 색상만으로 구분하지 않는다.

| AI 힌트 | 95백분위 10초 이내, 15초 후 대체 안내 |
| AI 코드 생성 | 95백분위 15초 이내, 20초 후 대체 안내 |

이 수치는 출시 목표이며 측정된 성능이 아니다.

## 12 성과 지표와 사용자 검증

핵심 지표는 시작한 학생이 두 트랙 이상을 체험하고 다음 행동을 선택하는 비율이다. 체험 종료는 코드를 수정하고 한 번 이상 실행한 뒤 회고를 제출한 상태로 정의하며, 모든 테스트 통과를 요구하지 않는다. 단순 페이지 열람과 정답 예시 열람만 한 경우는 체험 종료로 세지 않는다.

| 지표 | 정의 | 초기 목표 |
| --- | --- | --- |
| 첫 체험 종료율 | 첫 체험 종료 사용자 수 ÷ 첫 미션 시작 사용자 수 | 60% 이상 |
| 두 트랙 체험 및 다음 행동 선택률 | 서로 다른 두 트랙을 종료하고 후속 활동을 선택한 사용자 수 ÷ 첫 미션 시작 사용자 수 | 40% 이상 |
| 탐색 명확성 변화 | 두 트랙 종료 사용자의 사전 질문(F01)과 사후 질문의 동일한 5점 문항 비교 | 70% 이상이 1점 이상 상승 |
| 방식 구분도 | 방식별 흥미 최고점과 최저점의 차가 1점 이상인 트랙 종료 사용자 비율 | 50% 이상 |
| 추천의 구체성 | 두 트랙 종료 후 다음 행동과 이유를 직접 설명한 사용자 비율 | 70% 이상 |
| 주요 흐름의 기술 실패율 | 복구하지 못한 실행·저장·생성 오류 세션 수 ÷ 시작 세션 수 | 5% 미만 |

'방식 구분도'는 방식 축이 실제로 의미 있는 정보를 주는지 확인한다. 대부분이 세 방식에 같은 점수를 주면 방식 축을 줄이거나 미션을 다시 설계한다.

'추천의 구체성'은 사용자가 적은 다음 행동이 두 조건을 만족하면 인정한다. 과목명, 미션명, 프로젝트명 중 하나를 이름으로 말하고, 이유를 하나 이상 적어야 한다. 판정은 팀원 2명이 따로 하고, 의견이 다르면 협의한다.

모든 목표는 파일럿 후 조정할 제안값이다. 시작, 실행, 힌트, 지시, 체험 종료, 회고 제출, 비교 조회, 다음 행동 선택을 이벤트로 기록하고, 트랙·방식별 이탈 지점을 확인한다. 미완료 사용자도 후속 인터뷰에 포함한다.

### 사용성 파일럿

- 참가자는 학생 12명이다. 세 트랙의 순서 6가지에 2명씩 배치해 순서에 따른 차이를 살핀다.
- 한 명이 세 트랙을 모두 하므로 미션만 90~120분이고, 사전 질문과 회고를 더하면 약 105~135분이다. 2회로 나눠 참여하게 한다.
- 언어별 경험과 AI 도구 경험을 함께 보고 결과를 해석한다.
- 파일럿 참가자에게는 동의를 받아 연락처를 따로 받고, 7일 뒤 선택한 후속 활동을 실제로 시작했는지 확인한다. 공개 서비스의 비회원 사용자는 연락 수단이 없으므로 이 확인은 파일럿에만 적용한다.
- 소규모 관찰 결과로 전체 학생의 적성이나 취업 성과를 일반화하지 않는다.

## 14 후속 확장과 주요 결정

첫 버전에서 제외하는 항목은 실시간 멘토 매칭, 기업 채용 연계, 자격·적성 인증, 자유로운 프로젝트 생성, 여러 언어 지원, 네이티브 앱, 복잡한 관리자 화면, AI 코딩 도구 사용법 강의다.

검증 후에는 다음을 확장할 수 있다.

- 분야: 보안, 인프라, 모바일
- 방식: 여러 단계를 스스로 진행하는 AI 에이전트에게 작업을 맡기고 검토하기
- 심화 미션, 선택적 계정과 장기 회고

### 주요 결정

- 동일한 사례에서 세 분야를 경험하게 해 배경 이해 부담을 줄인다.
- 언어 체험은 유지한다. AI 결과를 판단하려면 언어와 분야를 알아야 하기 때문이다.
- 같은 분야 안에서 직접·검수·지시 세 방식을 모두 해보고 비교한다.
- 체험의 목표는 다음 학습 선택이며, 작업별 점수를 적성 점수로 환산하지 않는다.
- AI는 힌트, 회고, 지시 미션의 코드 생성에만 쓴다. 미션과 테스트 기준은 사전 검수한다.
- 언어 경험, AI 도구 경험, 자기 회고를 결과에 함께 표시한다.
- 첫 구현에서는 실행기와 한 트랙의 전체 흐름을 먼저 확인한다.

### 착수 시 확정할 항목

- [ ] 팀 인원과 해커톤 일정(6주보다 짧으면 13장 축소안 적용)
- [ ] 미션의 언어 난이도
- [ ] 지원 브라우저
- [ ] AI 제공사와 일일 비용 한도
- [ ] 방식 순서 고정 여부(파일럿 결과로 재검토)

문제 인터뷰와 첫 체험 검증 결과에 따라 바꾼다. 단, 미션을 직접 수행하고 비교한 뒤 다음 행동을 정한다는 핵심 흐름은 유지한다.
