# 개발 직무 맛보기 실험실 PRD 초안

개발 직무 맛보기 실험실은 컴퓨터학부 학생이 프론트엔드, 백엔드, 데이터 분석의 작은 작업을 직접 수행하고, 자신이 흥미를 느낀 과정과 어려웠던 지점을 비교하는 진로 탐색 서비스다. 첫 버전은 같은 학교 행사 서비스를 배경으로 세 가지 체험을 제공한다.

이 PRD는 구현을 위한 초안이다. 문제의 빈도와 사용자 반응은 검증할 가설로 두고, 첫 출시 범위와 수용 기준은 아래와 같이 제안한다. 목표는 학생이 다음에 시도할 학습이나 프로젝트를 선택하도록 돕는 것이다.

# 문제 상황 인식

컴퓨터학부 학생이 전공 수업을 들으며 개발 직무를 선택하려고 할 때, 직무 이름과 실제로 수행하는 작업 사이에 간격이 생길 수 있다. 프론트엔드가 화면을 만들고 백엔드가 서버를 만든다는 설명을 알아도, 자신이 어떤 문제를 푸는 과정에 흥미를 느끼는지는 별도의 경험이 필요하다.

다음은 검증할 대표 상황이다.

- 수업과 팀 프로젝트에서 맡아본 역할이 제한돼 다른 분야를 선택할 근거가 부족하다.

- 분야를 알아보려고 강의를 시작했지만 설치와 문법 학습에 시간을 쓰다가 실제 작업을 경험하기 전에 멈춘다.

- 처음 접한 언어나 도구가 어려웠던 경험을 그 분야 자체에 대한 흥미 부족으로 받아들인다.

- 콘텐츠를 본 뒤에도 다음 학기에 어떤 과목을 듣고 어떤 프로젝트를 해볼지 결정하지 못한다.

예상 사용자 발화는 “백엔드가 뭘 하는지는 대충 아는데, 내가 그 일을 좋아할지는 모르겠다”이다. 실제 인터뷰에서는 이 문장을 유도하지 않고 최근 직무 탐색 경험과 행동을 확인한다.

# 대상 사용자와 사용 시점

## 핵심 사용자

변수, 조건문, 반복문, 함수의 기초를 배운 컴퓨터학부 1학년부터 3학년 학생을 첫 대상으로 삼는다. 한 분야의 실무 능력을 평가받으려는 사람보다, 서로 다른 작업을 경험하며 다음 학습 방향을 고르려는 사람에게 집중한다.

| 사용자 | 현재 상황 | 원하는 변화 |
| --- | --- | --- |
| 전공 입문 학생 | 분야 이름은 알지만 직접 해본 일이 적다 | 흥미가 생기는 작업을 발견한다 |
| 첫 팀 프로젝트 준비 학생 | 프론트와 백엔드 중 역할을 정해야 한다 | 작은 경험을 바탕으로 역할을 선택한다 |
| 관심 분야를 바꾸려는 학생 | 한 분야만 경험해 다른 분야를 판단하기 어렵다 | 기존 경험과 새 작업을 비교한다 |

사용 시점은 수강 신청 전, 동아리나 팀 프로젝트의 역할 배정 전, 방학 학습 계획을 세울 때로 설정한다. 완전한 프로그래밍 입문 교육과 취업 역량 인증은 첫 버전의 대상에서 제외한다.

# 목표와 핵심 가치

사용자가 두 가지 이상을 체험한 뒤 “어떤 작업이 흥미로웠는지, 무엇 때문에 어려웠는지, 다음에 무엇을 해볼지”를 자신의 말로 설명하게 만드는 것이 제품의 목표다.

핵심 가치는 세 가지다.

1. 별도의 개발환경 설치 없이 작은 작업부터 시작한다.

2. 같은 서비스의 서로 다른 문제를 풀며 작업의 차이를 경험한다.

3. 실행 결과, 선택 이유, 자기 회고를 함께 보고 다음 행동을 정한다.

출시 버전에서는 프론트엔드, 백엔드, 데이터 분석을 제공한다. 데이터 분석은 진로 탐색용 별도 트랙이며 세 분야가 모든 개발 직무를 포괄한다고 표현하지 않는다.

# 문제 가설과 사전 검증

개발 전 컴퓨터학부 학생 8명 내외와 인터뷰한다. 학년과 기존 경험이 다른 학생을 포함하고, 아래 가설과 반대되는 사례도 함께 기록한다.

| 가설 | 확인할 질문과 행동 | 초기 판단 기준 |
| --- | --- | --- |
| 직접 해본 작업이 부족해 분야 선택이 어렵다 | 최근 분야를 선택하거나 포기한 과정, 참고한 근거를 묻는다 | 8명 중 5명 이상에게 구체적인 경험 부족 사례가 있으면 우선 해결한다 |
| 설치와 선행 학습이 체험을 지연한다 | 시작 후 실제로 무언가를 수정하기까지 걸린 과정과 포기 지점을 확인한다 | 반복되는 장애를 체험의 시작 흐름에서 제거한다 |
| 작은 작업도 다음 선택에 도움이 된다 | 첫 미션 시제품을 사용한 뒤 다음에 해보고 싶은 일을 설명하게 한다 | 막연한 직무 이름보다 구체적인 다음 행동이 나오는지 확인한다 |

이 기준은 프로젝트 진행을 위한 임시 기준이며 현재 조사 결과가 아니다. 경험 부족보다 채용 정보나 학습 비용이 더 큰 문제로 확인되면 대상 사용자와 제공 가치를 다시 좁힌다.

# 체험 콘텐츠 설계

## 공통 사례

공통 사례는 “교내 행사 신청 서비스 개선”으로 정한다. 학생은 트랙마다 다른 역할을 맡되 서비스의 배경과 용어를 다시 익힐 필요가 없게 한다. 실제 학생 개인정보 대신 제작한 예시 데이터만 사용한다.

| 트랙 | 요청받은 일 | 사용자가 직접 하는 작업 | 결과물 | 확인할 작업 성격 |
| --- | --- | --- | --- | --- |
| 프론트엔드 | 신청 가능한 행사를 쉽게 찾게 해주세요 | 제공된 HTML과 JavaScript의 필터 조건과 화면 상태를 수정한다 | 필터가 동작하는 행사 목록과 변경 이유 | 화면 반응 확인, 사용자 관점의 개선 |
| 백엔드 | 중복 신청과 정원 초과를 막아주세요 | 제공된 Python 신청 처리 함수의 검증과 응답을 수정한다 | 정상 신청과 예외 상황을 처리하는 함수 | 규칙 해석, 예외 조건, 데이터 일관성 |
| 데이터 분석 | 다음 행사 운영에서 무엇을 개선할지 알려주세요 | 예시 신청 데이터의 중복을 처리하고 참여율을 집계한 뒤 해석한다 | 집계 표와 근거가 포함된 개선 제안 | 데이터 정리, 비교 기준, 수치 해석 |

백엔드 체험은 요청과 응답을 흉내 낸 입력으로 서버의 업무 규칙을 다루는 활동이다. 실제 서버 배포나 동시 접속 처리는 포함하지 않는다. 데이터 분석도 모델 학습이 아닌 기초 집계와 해석을 다룬다.

이 활동 구분은 웹 개발의 구현·검증·요구 분석과 데이터 분야의 데이터 처리·시각화·해석 업무를 참고한 교육용 축약이다. 세부 직무와 실제 업무는 조직에 따라 달라질 수 있다. 참고: [O*NET Web Developers](https://www.onetonline.org/link/details/15-1254.00), [O*NET Data Scientists](https://www.onetonline.org/link/details/15-2051.00).

## 미션 구성과 난이도

각 트랙은 약 25분부터 35분의 체험을 목표로 설계한다. 이 시간은 사용성 테스트에서 조정하며 시간 제한이나 평가 점수로 사용하지 않는다.

1. 배경과 요청을 읽는다.

2. 필요한 문법을 3분 내외의 준비 예제로 확인한다.

3. 기존 코드를 실행하고 정상 상태를 확인한다.

4. 작은 수정 과제 두 개와 예외 상황 한 개를 해결한다.

5. 수정 이유를 짧게 설명한다.

6. 흥미, 체감 난이도, 다시 해보고 싶은 정도를 회고한다.

프론트엔드는 HTML과 JavaScript, 나머지 두 트랙은 Python을 사용한다. 온보딩에서 언어별 경험을 별도로 기록하고, 처음 접하는 언어에는 고정된 문법 안내를 제공한다. 트랙별 시간과 테스트 통과율을 서로 다른 언어 능력의 순위로 합산하지 않는다.

미션은 운영자가 사전 작성하고 검수한다. AI가 사용자마다 새로운 문제나 정답 기준을 만들어 난이도가 달라지는 방식은 초기 범위에 포함하지 않는다.

# 사용자 흐름과 화면

비회원 시작 → 언어 경험과 탐색 목적 입력 → 트랙 선택 → 준비 예제 → 작업 수행과 힌트 → 회고 → 개별 결과 → 다른 트랙 체험 → 비교 결과와 다음 활동 선택 순서로 진행한다.

| 화면 | 필요한 정보와 행동 |
| --- | --- |
| 시작 화면 | 무엇을 체험하는지, 예상 시간, 필요한 기초 지식, 설치 없이 시작하기 |
| 사전 질문 | Python·JavaScript 경험, 기존 프로젝트 역할, 비교해보고 싶은 분야 |
| 트랙 목록 | 각 트랙에서 실제로 할 작업, 준비 지식, 예시 결과물 |
| 작업 화면 | 요청사항, 코드 편집, 실행 결과, 테스트 결과, 힌트, 저장 상태 |
| 회고 화면 | 흥미·체감 난이도·재도전 의향을 각각 1점부터 5점으로 기록하고 이유 작성 |
| 개별 결과 | 수행한 작업, 테스트 결과, 사용한 도움, 본인 회고, 다음 작은 과제 |
| 비교 화면 | 두 트랙 이상의 회고와 결과를 나란히 확인하고 다음 활동 선택 |

트랙 순서는 사용자가 고를 수 있다. 첫 선택에 설명이 필요하면 직무 이름과 함께 “화면 반응 만들기”, “신청 규칙 만들기”, “숫자에서 개선점 찾기”를 보여준다. 한 트랙을 마쳐도 다른 트랙을 강제로 시작시키지 않는다.

| ID | 우선순위 | 요구사항 | 수용 기준 |

| F01 | P0 | 비회원 체험 | 가입 절차 없이 미션을 시작하고 언어 경험과 탐색 목적을 기록한다 |
| F02 | P0 | 사전 검수한 세 트랙 | 트랙마다 목표, 준비 예제, 시작 코드, 검증 사례, 고정 힌트, 회고 항목이 존재한다 |
| F03 | P0 | 코드 편집과 결과 확인 | 사용자가 코드를 수정하고 실행해 화면 또는 함수·집계 결과의 변화를 확인한다 |
| F04 | P0 | 기준에 따른 검증 | 같은 코드와 같은 미션 버전에 같은 테스트 결과를 표시하고, 실패한 입력과 이유를 제공한다 |
| F05 | P0 | 단계별 도움 | 준비된 힌트와 AI 질문 기능을 제공하고 사용한 도움 단계를 기록한다 |
| F06 | P0 | 저장과 이어하기 | 수정 후 1초 지연 저장을 시도하며 새로고침 후 마지막 저장 성공 지점으로 복구한다 |
| F07 | P0 | 종료와 회고 | 전부 통과하지 않아도 체험을 종료하고 어려웠던 이유와 흥미를 남길 수 있다 |
| F08 | P0 | 개별 결과와 비교 | 한 트랙은 개별 결과, 두 트랙 이상은 비교 결과를 제공하며 없는 결과를 추정해 채우지 않는다 |
| F09 | P0 | 다음 활동 제안 | 검수된 후속 미션이나 학습 주제 중 사용자가 다음 활동을 선택하고 이유를 저장한다 |
| F10 | P0 | 오류와 사용량 대응 | AI·실행기·저장 오류를 구분하고 기존 작업을 보존한 채 복구 방법을 안내한다 |
| F11 | P0 | 체험 기록 삭제 | 사용자가 자신의 익명 체험 기록을 삭제할 수 있다 |
| F12 | P1 | 장기 보관과 공유 | 선택적 로그인, 다른 기기에서 이어하기, 개인이 선택한 결과 공유를 지원한다 |

미션은 코드, 예시 데이터, 검증 기준, 고정 힌트, 검토자를 포함한 버전 단위로 배포한다. 진행 중인 세션은 시작 당시 버전을 유지하고, 오류가 심각한 미션은 새 시작을 중단한다. 콘텐츠 운영은 저장소의 검수된 파일로 처리하며 별도 관리자 화면은 초기 범위에서 제외한다.

# AI API 활용 요구사항

## AI의 역할

AI는 사용자가 작업을 이해하고 자신의 경험을 되짚는 데 사용한다. 코드의 실행 결과와 테스트 통과 여부는 정해진 실행기와 검증 코드가 판단한다.

| 기능 | 입력 | 출력 | 제한 |
| --- | --- | --- | --- |
| 단계별 힌트 | 미션 단계, 현재 수정 내용, 실패 사례, 이전 힌트 | 개념 설명, 확인할 위치, 작은 예시 순서의 도움 | 첫 응답부터 전체 정답을 제공하지 않는다 |
| 오류 설명 | 실제 실행 오류와 검증 결과 | 쉬운 원인 설명과 다음 확인 항목 | 기록에 없는 오류나 실행 결과를 만들지 않는다 |
| 선택 이유 질문 | 사용자의 수정 결과와 설명 | “이 경우에는 어떻게 될까요”와 같은 후속 질문 | 직무 적합성이나 성격을 판정하지 않는다 |
| 회고 요약 | 수행 기록, 자기 평가, 사용자가 적은 이유 | 작업별 흥미와 어려움, 다음 활동 후보 | 관찰 사실과 사용자 응답을 구분해 설명한다 |

예시 응답은 “중복 신청 처리는 통과했고 정원 초과 사례는 아직 남아 있어요. 남은 자리를 확인하는 조건부터 살펴볼까요?”처럼 실제 테스트 기록을 근거로 한다.

## 호출과 품질 관리

AI API는 서비스 서버를 통해 호출한다. 브라우저에 API 키를 전달하지 않는다. 초깃값은 트랙당 힌트·질문 6회와 회고 요약 1회, 비교 요약 1회로 제한한다. 총 세 트랙을 체험하면 최대 22회다. 같은 실패 상황의 고정 설명은 재사용하고, 운영자가 전체 일일 비용 한도를 설정한다.

힌트 응답은 짧은 설명과 다음 행동, 참조한 단계 ID를 포함한 구조로 받는다. 서버는 형식과 참조 ID를 검사하고 출력 길이를 제한한다. 사용자 코드와 문장은 분석할 자료로 전달하고 시스템 지시와 분리한다. 응답의 지시를 실행하거나 코드에 자동 적용하지 않는다.

입력은 현재 단계의 변경 코드와 필요한 실행 기록으로 한정한다. 한 요청의 코드·자유 입력 합계는 2만 자 이내로 제한하고 긴 로그는 오류 주변만 전달한다. 모델과 제공사는 한국어 설명 품질, 제한된 입력에서의 일관성, 지연, 실제 비용을 평가한 뒤 선정한다.

출시 전 최소 30개 사례로 힌트와 요약을 확인한다. 정상 풀이, 미완료, 문법 오류, 과도한 정답 요구, 지시 우회 문구, 빈 회고를 포함한다. 기록과 다른 성공 주장이나 적성 단정이 나온 사례는 출시 전 수정하고 재검증한다.

# 결과 리포트와 추천 기준

결과는 작업 기록과 자기 회고를 함께 보여준다. “백엔드 적합도 92점” 같은 종합 적성 점수나 직무 순위는 만들지 않는다.

| 구분 | 표시할 내용 | 해석 원칙 |
| --- | --- | --- |
| 수행 기록 | 시도한 단계, 검증 사례별 통과 여부, 완료·미완료 상태 | 해당 미션의 결과로 한정한다 |
| 도움 기록 | 사용한 힌트 단계, 정답 예시 열람 여부 | 실력 감점으로 사용하지 않는다 |
| 자기 회고 | 흥미, 체감 난이도, 재도전 의향, 자유 서술 | 사용자의 응답임을 표시한다 |
| 비교 맥락 | 언어 경험, 준비 예제 수행, 미션 버전 | 다른 트랙의 수치와 단순 우열 비교를 피한다 |
| 다음 행동 | 다음 작은 미션, 보충할 기초, 다른 트랙 체험 | 사전 검수한 활동 목록에서 제안한다 |

다음 행동은 고정 규칙으로 후보를 정하고 AI가 설명을 돕는다. 재도전 의향이 4점 이상이면 같은 작업을 확장하는 미션을, 흥미 4점 이상이면서 체감 난이도도 4점 이상이면 짧은 기초 보충과 재체험을 제안한다. 한 트랙만 수행했거나 회고가 비어 있으면 비교 판단을 보류한다.

각 결과에는 수정한 작업과 회고를 다시 열 수 있는 근거를 연결한다. AI가 기록과 맞지 않게 요약하면 사용자가 수정하거나 신고할 수 있고, 원래 기록은 유지한다.

# 구현 방향과 데이터

## 권장 구성

브라우저 기반 웹 서비스로 구현한다. 화면과 코드 편집기는 React와 TypeScript를 후보로 두며, 서버는 팀이 익숙한 프레임워크 한 가지를 선택해 세션·콘텐츠·AI 호출·비용 기록을 맡긴다. AI를 위해 별도 서비스를 추가하는 것은 초기 필수 조건이 아니다.

프론트엔드 코드는 서비스 화면과 분리된 실행 영역에서 표시하고, 백엔드·데이터 체험의 Python은 브라우저 실행기를 후보로 검증한다. Pyodide는 Web Worker에서 Python을 실행하는 방식을 제공하므로 기술 검증에 사용할 수 있다. 실제 패키지 크기, 최초 로딩, 브라우저 호환성은 1주차에 측정한다. 참고: [Pyodide Web Worker 공식 문서](https://pyodide.org/en/stable/usage/webworker.html).

사용자 코드를 서비스 서버 프로세스에서 직접 실행하지 않는다. Python의 Worker만으로 보안 격리가 완성된다고 가정하지 않고, 실행 영역은 별도 출처로 분리하고 인증 정보와 저장소 접근을 차단한다. 외부 통신은 실행 환경 초기화에 필요한 정적 자원으로 제한하고, 초기화 이후 사용자 코드의 외부 통신은 차단한다. 실행 영역과 서비스 사이에는 허용한 메시지 형식만 주고받는다.

실행 제한의 초기 기준은 1회 5초이며 초과하면 실행 영역을 종료·재생성한다. 대용량 데이터와 임의 패키지 설치는 지원하지 않는다. 브라우저 자원 소모와 격리를 검증하지 못하면 임의 코드 체험을 공개하지 않고 비공개 기술 시제품에서 먼저 해결한다.

개발 목표는 미션 조회의 95백분위 응답 2초 이내, AI 힌트 95백분위 10초 이내, 15초 후 대체 안내 제공이다. 실행기 최초 다운로드는 별도 지표로 측정한다. 이 수치는 출시 목표이며 측정된 성능이 아니다.

# 성과 지표와 사용자 검증

핵심 지표는 시작한 학생이 두 트랙 이상을 체험하고 다음 행동을 선택하는 비율이다. 체험 종료는 코드를 수정하고 한 번 이상 실행한 뒤 회고를 제출한 상태로 정의하며, 모든 테스트 통과를 요구하지 않는다. 단순 페이지 열람과 정답 예시 열람만 한 경우는 체험 종료로 세지 않는다.

| 지표 | 정의 | 초기 목표 |
| --- | --- | --- |
| 첫 체험 종료율 | 첫 체험 종료 사용자 수 ÷ 첫 미션 시작 사용자 수 | 60% 이상 |
| 두 트랙 체험 및 다음 행동 선택률 | 서로 다른 두 트랙을 종료하고 후속 활동을 선택한 사용자 수 ÷ 첫 미션 시작 사용자 수 | 40% 이상 |
| 탐색 명확성 변화 | 두 트랙 종료 사용자의 체험 전후 동일한 5점 질문 비교 | 70% 이상이 1점 이상 상승 |
| 추천의 구체성 | 두 트랙 종료 후 다음 행동과 이유를 직접 설명한 사용자 비율 | 70% 이상 |
| 주요 흐름의 기술 실패율 | 복구하지 못한 실행·저장 오류 세션 수 ÷ 시작 세션 수 | 5% 미만 |

모든 목표는 파일럿 후 조정할 제안값이다. 시작, 실행, 힌트, 체험 종료, 회고 제출, 비교 조회, 다음 행동 선택을 이벤트로 기록하고 트랙별 이탈 지점을 확인한다. 미완료 사용자도 후속 인터뷰에 포함한다.

사용성 파일럿은 학생 12명으로 시작한다. 여섯 가지 트랙 순서에 두 명씩 배치해 순서에 따른 차이를 살펴보고, 언어별 경험과 함께 결과를 읽는다. 한 번에 약 60분부터 90분의 부담이 있으므로 분할 참여를 허용한다. 소규모 관찰 결과로 전체 학생의 적성이나 취업 성과를 일반화하지 않는다.

7일 뒤 선택한 후속 활동을 실제 시작했는지 확인한다. 재방문 자체보다 진로 탐색의 다음 행동으로 이어졌는지 보조 지표로 살핀다.

# 개발 순서와 출시 조건

4명이 6주간 진행한다는 계획 가정으로 일정을 구성한다. 실제 인원과 기간이 달라지면 트랙 수와 콘텐츠 깊이를 조정한다.

| 기간 | 구현과 검증 | 완료 기준 |
| --- | --- | --- |
| 1주차 | 문제 인터뷰, 세 미션 설계, 실행기·격리 기술 검증 | 대상 문제 확인, 최소 미션 실행, 코드 격리와 중단 가능 여부 확인 |
| 2주차 | 한 트랙의 시작부터 결과까지 구현 | 편집·실행·검증·저장·회고가 연결된다 |
| 3주차 | 나머지 두 트랙과 비교 결과 구현 | 세 콘텐츠 버전 검수와 두 트랙 비교가 가능하다 |
| 4주차 | AI 힌트·회고, 호출 한도, 장애 대체 흐름 | AI 없이도 체험이 가능하고 기록과 다른 출력 사례를 수정한다 |
| 5주차 | 사용자 파일럿과 콘텐츠 조정 | 난이도·언어·이탈 원인을 확인하고 핵심 장애를 수정한다 |
| 6주차 | 재검증, 지원 환경 점검, 시연 준비 | P0 수용 기준과 출시 조건을 통과한다 |

담당은 화면과 실행기, 서버와 데이터, 미션 콘텐츠와 검증, AI와 사용자 조사로 나눌 수 있다. 미션 검토는 작성자 외 한 명이 맡는다.

공개 출시 조건은 세 트랙의 기준 풀이와 검증 사례 통과, 저장·복구 확인, 무한 반복과 외부 접근 제한 확인, AI 장애 대체 동작 확인, 비용 한도와 삭제 기능 확인이다. 사용자 파일럿에서 첫 수정까지 도달하지 못하는 장애가 남으면 공개 범위를 늘리기 전에 해결한다.

# 후속 확장과 주요 결정

첫 버전에서 제외하는 항목은 실시간 멘토 매칭, 기업 채용 연계, 자격·적성 인증, 자유로운 프로젝트 생성, 여러 언어 지원, 네이티브 앱, 복잡한 관리자 화면이다. 검증 후에는 보안·인프라·모바일 등 작업 종류, 심화 미션, 선택적 계정과 장기 회고를 확장할 수 있다.

기획의 주요 결정은 다음과 같다.

- 동일한 사례에서 세 작업을 경험하게 해 배경 이해의 부담을 줄인다.

- 체험의 목표는 다음 학습 선택이며, 작업별 점수를 적성 점수로 환산하지 않는다.

- AI는 힌트와 회고에 집중하고 미션·테스트 기준은 사전 검수한다.

- 언어 경험과 자기 회고를 결과에 함께 표시한다.

- 첫 구현에서는 실행기와 한 트랙의 전체 흐름을 먼저 확인한다.

착수 시 확정할 항목은 팀 인원과 일정, 미션의 언어 난이도, 지원 브라우저, AI 제공사와 비용 한도다. 문제 인터뷰와 첫 체험 검증 결과에 따라 변경하되, 미션을 직접 수행하고 비교한 뒤 다음 행동을 정한다는 핵심 흐름을 유지한다.
